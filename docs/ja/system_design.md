# OpenTSRのシステム設計：切り替え可能な量産相当のパイプライン（ドラフトv0、2026-11-01）

> 本文書は英語版 [docs/system_design.md](../system_design.md) の日本語訳である（原文 commit 52837a8 時点）。内容に食い違いがある場合は英語版を正とする。

状態：議論用のドラフト。`benchmark.md`（何を測定するか）および`commercial_tsr.md`（量産システムが何をするものとして文書化されているか）と対をなす文書である。本ファイルは、OpenTSRをシステム全体として、また各部分のアブレーションとして評価できるようにどう構築するか、そしてそれに対して敵対的攻撃をどう評価するかを述べる。

## 1. 設計目標

1. 量産TSRの構造（検出、追跡、記憶、分類、読み取り、関連性判定、事前情報の融合）を、オープンなコード、オープンなデータ、オープンな重みで再現する。
2. すべてのステージを設定ファイルから無効化または置換できるようにし、アブレーションドライバを1回実行するだけで、各ステージが精度、ロバスト性、コストに与える寄与を定量化できるようにする。
3. 敵対的評価も同じ設定の仕組みを用いる。攻撃は単一のステージ、フレーム単位のペア（検出器と分類器）、システム全体のそれぞれに対して実行し、防御も他と同じく一つのステージとして扱う。
4. 車載で動作するものはすべて、ONNXとINT8にエクスポートできるCNNまたは小規模なシーケンスモデルとする。TransformerとVLMはオフライン（ラベル付け、生成、候補の発掘）で用いる。

## 2. パイプラインとステージ

```
frame ──► Detector ──► Tracker ──► Memory ──► Classifier ──► Reader ──► Relevance ──► Fusion ──► Decision ──► messages
            │             │          │            │             │           │            │
         boxes +       tracks     persisted    fine class +   digits /    applies to   map / road
         coarse class  (ids)      signs        confidence     text        ego lane?    type prior
```

各ステージは、一つのメソッドと宣言された入出力スキーマを持つPythonクラスである。設定で`null`を指定するとそのステージは取り除かれ、入力がそのまま次に渡される。中間出力はフレームごとにJSON Linesとして書き出し、後の分析を再実行なしで行えるようにする。

| ステージ | 目的 | 予定している選択肢（最初の項目がデフォルト） | 無効時の動作 |
|---|---|---|---|
| 検出器（Detector） | フレーム全体から標識候補を見つける | 粗粒度クラスを出力する1280 pxのワンステージCNN（YOLOXファミリー、Apache-2.0）；2048 pxのタイル分割；比較用にRT-DETRv2 / D-FINE；候補の発掘用にオフラインでOWLv2；クラスの粒度：粗粒度 / 単一クラス / 細粒度 | 該当なし（常に存在する） |
| トラッカー（Tracker） | フレーム間で候補を対応づけ、1フレームだけの検出を抑制する | IoUトラッカー；ByteTrack（MIT）；カルマン予測による対応づけ；kフレーム後に確定 | 各フレームを独立に扱う |
| メモリ（Memory） | 認識した標識を通過するまで保持する | 自車速度またはビジュアルオドメトリを用いた位置ベースの消去；時間ベースのTTL；なし | 標識が見えている間だけ出力が存在する |
| 分類器（Classifier） | 位置合わせしたクロップに対して細粒度クラスを判定する | 固定マージン付き、64〜96 pxのConvNeXt-atto級CNN；STN-CNN；ViT（参照用）；マルチクロップまたはTTA；アンサンブルの一致；信頼度またはエネルギーによる未知クラスの棄却 | 検出器の粗粒度クラスをそのまま出力する |
| リーダ（Reader） | 数字と文字 | 速度、重量、高さの標識と補助標識に対するOCRヘッド（PARSeq方式、Apache-2.0）；分類器との整合性チェック；可変表示標識 | 分類器の出力のみ |
| 関連性判定（Relevance） | その標識が自車に適用されるか | 幾何的なヒューリスティック（横方向オフセット、サイズの増加、車線位置）；LISAの"on side road"、MTSDの"direction-or-information"、OpenTSRのラベルで学習したヘッド | すべての標識を関連ありとする |
| 融合（Fusion） | 事前情報と暗黙の制限 | GNSSを介したOSMのmaxspeed；暗黙の制限のための道路種別分類器；矛盾時のルール（明示的な標識ではカメラを優先） | カメラのみ |
| 判断（Decision） | メッセージストリーム | トラック全体での投票（多数決、信頼度重み付き、ベイズ）；ヒステリシス；出力前に必要な最小限の証拠 | フレーム単位のargmax |
| 防御（Defense） | 任意の堅牢化 | 入力の浄化（JPEG、ビット深度、メディアン）；敵対的学習した分類器；検出器、分類器、リーダ間の一致チェック；時間的一貫性；パッチ検出器 | なし |

設定例（`configs/system/full.yaml`）：

```yaml
detector:   {type: yolox_coarse, weights: weights/opentsr/det_v1.onnx, input: 1280, classes: coarse_v1}
tracker:    {type: bytetrack, confirm_frames: 3}
memory:     {type: position, clear_after_pass_m: 5}
classifier: {type: convnext_atto, weights: weights/opentsr/cls_de_v1.onnx, crop_margin: 0.15, reject_below: 0.6}
reader:     {type: parseq_digits, weights: weights/opentsr/ocr_v1.onnx, agree_with_classifier: true}
relevance:  {type: geometric, max_lateral_offset_m: 6.0}
fusion:     {type: osm_prior, source: data/osm/jp_maxspeed.pbf}
decision:   {type: weighted_vote, min_frames: 3, hysteresis: 0.2}
defense:    null
```

`configs/system/academic.yaml`はベースラインの設定である：細粒度クラスの検出器、他のステージはすべて`null`、フレーム単位のargmax。アブレーションドライバ（`scripts/run_ablation.py`、未作成）は、基本設定とステージのリストを受け取り、「すべて有効」「一つずつ無効」「一つずつ有効」および名前付きのプリセットを実行し、設定ごとにL1〜L3の指標、ロバスト性の列、レイテンシをまとめた一つの表を書き出す。

## 3. モデルと分類体系

- 粗粒度の分類体系（`configs/taxonomy/coarse_v1.yaml`、未定義）：どの国にも存在する形状と色のファミリー。例えば、禁止（赤い円形）、義務（青い円形）、警戒（三角形）、警戒（ひし形）、優先（譲れ、優先道路）、一時停止、案内（長方形）、補助標識、その他。各データセットには、そのデータセット独自のラベルからの対応表を付ける。検出器は、この分類体系に対応づけたすべての検出セットの和集合で学習する。
- 地域ごとの細粒度の分類体系：ドイツはGTSRBの43、欧州はZODの156、日本は道路標識令の番号、世界共通の参照マップとしてMTSDの400ラベル。分類器は地域ごとに一つのモデルとするか、地域別のヘッドを持つ一つのモデルとする。いずれの場合も、検出器に手を加えずに置き換えられる。
- 学習データの方針：公開する重みは再配布可能なセットで学習する。非商用のセットは参照用の評価にのみ用いる（`decisions.md`、ベンチマークのティア）。
- 合成データ：ドイツはSynset Signset、日本は221種のMLITピクトグラムを同じ方法でレンダリングしたもの、L3のアブレーションにはCARLAのシーケンス。合成データのみの行と、合成データに実データを加えた行は分けて報告する。

## 4. コストと展開

- 車載のステージはすべてONNXにエクスポートし、キャリブレーションまたはQATでINT8化する。エクスポート後の精度を浮動小数点での数値と並べて報告する（Vitis AIのリファレンスと同様。YOLOX-mでfloat 62.3に対しINT8 62.1）。
- ベンチマークの入力サイズで、Jetson Orin級のデバイスとCPUにおける、ステージごとおよびパイプライン全体のレイテンシ表を作る。守るべき予算は5〜20 TOPSのフロントカメラ級である（`commercial_tsr.md`のB節）。
- Transformer系の検出器は、同じエクスポートとレイテンシの列を持つ比較用の行としてベンチマークに残し、コストに関する議論を実測で裏付ける。

## 5. 敵対的評価とロバスト性評価

### 5.1 脅威モデルとレベル

| レベル | 対象 | 攻撃者の知識 | 典型的な攻撃 |
|---|---|---|---|
| クロップ | 分類器（およびリーダ） | ホワイトボックス | クロップに対するPGD / C&W；印刷可能なパッチ（RP2、MIT）；クロップ変換に対するEOT |
| フレーム | 検出器 + 分類器 | クロップを通して勾配を流すためにROIAlignを用いたホワイトボックス；公開されたOpenTSRの重みを用いたグレーボックス | 標識上のShapeShifter（BSD-3）方式のパッチ；隠蔽（検出の抑制）、改変（誤ったクラス）、出現（標識が存在しない場所に標識に似たパッチ）；物理的に実現可能な摂動としてのSLAP（GPL-3.0、レーザ）、ShadowAttack（MIT） |
| イベント | トラッカー、メモリ、関連性判定、融合を含むシステム全体 | ブラックボックス / 学術的な代理モデル（Faster R-CNN、YOLO、RT-DETR）からの転移；シーケンスのフレームにわたる期待値 | 同じ攻撃をトラックに沿ってレンダリングしたもの；看板や画面上に出現するファントム標識；記憶を悪用するタイミング攻撃 |

イベントレベルは微分不可能（追跡、投票、メモリ）であるため、転移と、シーケンスにわたる期待値の最適化によって攻撃する。これは量産車を対象としたNDSS 2025のブラックボックス研究（`commercial_tsr.md`のA.5）の設定である。OpenTSRは、その研究ではできなかったことを加える：各ステージを無効化し、攻撃成功率がどう変化するかを測定する。

### 5.2 物理的攻撃のレンダリング

- 実画像：クロップレベルとフレームレベルには、REAP（幾何変換と照明変換を伴う、Mapillaryの標識上での現実的な敵対的パッチのベンチマーク。ライセンスは要確認）を用いる。
- シーケンス：イベントレベルには、標識のアクタに敵対的テクスチャを適用し、天候と距離を変化させたCARLAの走行を用いる。攻撃を再現できるよう、レンダリングパイプラインを公開する。
- 物理的な確認：印刷したパッチと閉鎖コースでの実走行。最も強い攻撃の転移を最終確認する場合にのみ行う。

### 5.3 評価指標

- 各レベルでの攻撃成功率。隠蔽、改変、出現の目的別に分けて求める。
- マトリクス：攻撃×レベル×システム構成（ステージの有効・無効）×代理モデル。
- 各防御構成がクリーン精度に与えるコスト。同じアブレーション実行から求める。
- 攻撃者のコスト：パッチサイズ、攻撃が持続しなければならないフレーム数、物理的制約。
- 自然なロバスト性も同じ表に載せ（CURE-TSRのレベル、GTSRBの劣化、CURE-TSDとCARLAの天候）、敵対的な劣化と自然な劣化を一つの尺度で比較できるようにする。

## 6. 本設計が裏付けることを意図した主張

1. L1とL2において、OpenTSRのモデルは再学習した学術的ベースラインと少なくとも同等である（モジュール型の設計や粗粒度検出器による性能低下がない）。
2. L3において、システム全体は同等以上のモデルをフレーム単位で展開した場合を上回り、アブレーション表はその改善を追跡、メモリ、関連性判定、リーダに帰属させる。
3. 単一モデルで測定した攻撃成功は、システムに対するリスクを過大に、あるいは誤って評価する。記憶によって隠蔽は難しくなり出現は容易になるが、アブレーションはその程度を示す。
4. 公開するシステムは、INT8エクスポート後に、明示した計算予算を満たす。

## 7. リスクと緩和策

- イベントの正解データ付きのシーケンスデータは少なく、一部は再配布できない：STSとCARLAから始め、イベント変換ツールを公開し、日本で収集するデータを長期的なアセットとする。
- 関連性のラベルは少ない：LISAとMTSDの属性で弱いヘッドを立ち上げる。日本のアノテーションプロトコルには最初から関連性を含める。
- 粗粒度検出器は細粒度クラスでの失敗を覆い隠しうる：検出器と分類器のペアの細粒度クラスL2の数値を、常に細粒度クラスの検出器と並べて報告する。
- CARLAの結果は実態より良く見えることがある：合成データで得た知見はすべて、少なくとも一つの実シーケンスのセットで確認する。
