# OpenTSRベンチマーク仕様（ドラフトv0、2026-11-01）

> 本文書は英語版 [docs/benchmark.md](../benchmark.md) の日本語訳である（原文 commit 52837a8 時点）。内容に食い違いがある場合は英語版を正とする。

状態：議論用のドラフト。合意が得られたら、いずれかのモデルをこれに合わせて調整する前に本ファイルを凍結し、以後の変更は日付付きの修正として末尾に記録する。本ベンチマークの目的は、OpenTSRが次の三つの主張を根拠とともに示せるようにすることである：（1）OpenTSRの検出器と分類器は、標準的な画像単位のベンチマークにおいて、学術研究で用いられる手法と少なくとも同等である。（2）量産システムと同じ方法（検出、追跡、記憶、分類、読み取り、関連性判定）で構築したシステム全体は、製品にとって重要な指標（標識通過イベント単位）でより優れている。（3）システムは、自然な劣化と敵対的攻撃に対して単一モデルより測定可能な程度にロバストであり、各構成要素の寄与はそれを無効化することで定量化される。

## 1. 三つの層

| 層 | 評価の単位 | 比較対象 | 存在理由 |
|---|---|---|---|
| L1クロップ分類 | クロップした標識1枚 | OpenTSRの分類器と学術的な分類器 | GTSRB時代の研究と同じ土俵；低コスト；分類器を切り分けて評価できる |
| L2単一フレームの検出と細粒度分類 | ボックス付きのフレーム1枚 | OpenTSRの検出器 + 分類器（追跡なし）と学術的な検出器 | TT100K / MTSD / GTSDBの研究と同じ土俵；システムレベルの改善を主張する前に、性能低下がないことを示す |
| L3シーケンス中の標識通過イベント | 自車が通過した物理的な標識1個 | OpenTSRのシステム全体と、同じモデルをフレームごとに適用したもの | 製品の指標（EU ISA、Euro NCAP）；追跡、記憶、関連性判定、OCRが価値を発揮する場 |

ロバスト性（自然な劣化と敵対的攻撃）は、三つの層すべてで同じ分割を用いて測定し、「クロップに対する攻撃成功」と「イベントに対する攻撃成功」を並べて比較できるようにする。

## 2. 層ごとのデータ

評価指標：細粒度クラス別、粗粒度カテゴリ別、およびクラス非依存の、VOC AP50とIoU 0.5:0.95でのCOCO方式AP。標識サイズの区分別の再現率（長辺が<16、16-31、32-47、48-63、64-95、96-127、128+ px。`dataset_catalog.md`と同じ）。すべてリポジトリ内の評価器（`src/opentsr/metrics.py`を拡張したもの）で計算し、フレームワーク独自の検証器は決して用いない。

### L3（シーケンスと標識通過イベント）

| セット | 役割 | ライセンス / アクセス | 状態 |
|---|---|---|---|
| Swedish Traffic Signs（STS） | 実シーケンス、5フレームごとにラベル、7クラス | CC BY 4.0（2026年のZenodoアップロード；CVLに要確認） | ダウンロード予定（15.8 GB） |
| ZOD Sequences / Drives | 実シーケンス、14か国 | CC BY-SA 4.0（要登録） | フレームごとのアノテーションの網羅範囲は要確認 |
| BelgiumTS detectionのシーケンス | 8台のカメラによる実シーケンス | 引用の要請のみ | フレーム番号の付け方とシーケンスの構造は要確認 |
| CURE-TSD | フレームごとのボックスと12種のチャレンジを含む、実（BelgiumTS由来）およびUnreal Engineの動画 | 申請フォーム；ライセンスは要確認 | 劣化を制御した唯一の大規模シーケンスセット |
| CARLAの合成走行 | 完全に制御されたシーケンス（標識の配置、天候、敵対的テクスチャ） | MIT（シミュレータ） | OpenTSRが生成；アブレーションと物理的攻撃のシミュレーションに用い、唯一の根拠としては決して用いない |
| OpenTSRの日本走行データ | GNSSとイベントの正解データ付きのドライブレコーダーのシーケンス | CC BY 4.0（公開予定） | 日本トラックの主要なアセット |

イベントの正解データ：自車が通過した物理的な標識インスタンスごとに一つのレコードを作り、細粒度クラス、OpenTSRの粗粒度クラス、関連性（自車線または自車の道路に適用されるか：あり、なし、不明）、標識が初めて12 px以上になるフレーム、通過フレーム（標識が視野から外れるか、自車がその位置を通過するフレーム）、さらに速度制限については通過後に有効な制限値を記録する。アノテーションプロトコルと、トラックID付きのフレームごとのボックスからの変換ツールはリポジトリに含める（`scripts/events_from_tracks.py`、未作成）。トラックIDを持たずフレームごとのボックスしかないセットには、単純なIoUリンカでトラックIDを付与する。このリンカ自体も公開し、シードを固定する。

評価指標（システムが出力するメッセージ{time, class, confidence, state}のストリーム上で定義する）：

- イベント再現率：関連性のあるイベントのうち、最初に見えたフレームから通過後2.0秒まで（ISAのウィンドウ）の間にシステムが正しい細粒度クラスを出力し、通過までそれを維持した（クラスが変化しない）ものの割合。
- イベント適合率と1 kmあたりの誤警報：どのイベントとも一致しない標識メッセージの出力（走行1 kmあたり）。関連性のない標識によるメッセージ（関連性判定の誤り）と、何もないところから生じたメッセージを分けて数える。
- 距離ベースの速度制限の精度：システムの現在の制限値が実際に有効な制限値と一致している走行距離の割合（ISAの90%という数値）。経路の制限値がアノテーションされている区間で計算する。
- 判断レイテンシ：最初に見えた時点から最初の正しく安定した出力までの時間、および通過から最終出力までの時間。
- 安定性：イベントあたりのクラスの反転回数。
- 再現率と適合率の粗粒度カテゴリ版。細粒度の分類体系が異なるシステムどうしを比較するために用いる。

L3における学術的ベースラインは、追跡を行わないフレーム単位のモデルである：メッセージストリームは各フレームでの標識ごとの最上位の検出であり、これはまさに単一モデルの論文が展開する場合のやり方である。

## 3. ロバスト性評価プロトコル

- 自然な劣化：L1ではGTSRBの劣化版コピーとCURE-TSR、L3ではCURE-TSDのチャレンジシーケンスとCARLAの天候スイープ。チャレンジの種類とレベルごとに指標を報告する。
- 敵対的攻撃：`system_design.md`の第5節に挙げた攻撃の下での同じ指標を、三つの層で、攻撃者の知識を明示して測定する（ステージに対するホワイトボックス、公開されたOpenTSRのチェックポイントを代理モデルとするグレーボックス、学術的な代理モデルからのブラックボックス転移）。
- ロバスト性の数値はすべて、クリーンな条件での数値と並べ、システム構成（どのステージが有効だったか）を列として示して報告し、防御のコストが見えるようにする。

## 4. 再実装するベースライン（同じデータ、同じ分割、同じ評価器）

分類：Udacity LeNet-5、poojahira STN-CNN（`replication.md`に既出）、ConvNeXt V2 atto（Hubのチェックポイントと再学習版）、ViT-B/16（標識を考慮したレシピで再学習、反転なし）、CLIP ViT-B/16のファインチューニングと線形プローブ。

検出：細粒度クラスを用いるYOLOX-s/m（Apache-2.0）とYOLO11n/s（AGPL、ベースラインのみ）。GTSDB時代の参照としてFaster R-CNN（torchvision）。Transformer系の検出器としてRT-DETRv2とD-FINE（Apache-2.0）。いずれも640 pxと1280 pxで評価し、いずれもINT8にもエクスポートして、エクスポート後の精度を報告する。

ゼロショットとオープン語彙の参照：OWLv2、YOLO-World、CLIPのゼロショット（測定済み）。

## 5. 報告ルール

- すべての表に、固定された公開分割、シード、コミットハッシュを記載する。OpenTSRが学習するものはすべて3シードで実行し、平均と標準偏差を示す。
- 数値は、`runs/`以下にJSONを書き出す`scripts/`のエントリポイントから得る。表は手入力せず、それらのファイルから生成する。
- レイテンシとメモリは、少なくとも二つのターゲット（NVIDIA Jetson Orin級のデバイスとCPU）で、エクスポート経路（ONNX、TensorRT）と数値精度を明記して報告する。
- 非商用データセット（TT100K、MTSD、DFG、LISA）は参照用の列として掲載し、OpenTSRが再配布するものには決して含めない。
