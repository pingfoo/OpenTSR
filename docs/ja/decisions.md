# 決定事項

> 本文書は英語版 [docs/decisions.md](../decisions.md) の日本語訳である（原文 PR #7 `phase0-skeleton` 時点）。内容に食い違いがある場合は英語版を正とする。

日付付きの記録：何を決定したか、その理由、検討した代替案。新しいものほど後ろに置く。

信号機トラックのみに関わる決定は`traffic_lights/docs/decisions.md`にある。

## 2026-10-31：まず調査し、次に再現する。クラウドセッションは推論専用とする

決定：最初のマイルストーンは、公開データセットとオープンソース実装の調査をまとめた文書（信号機については`traffic_lights/docs/datasets.md`、`traffic_lights/docs/oss_implementations.md`）とし、続いて重みと評価データが入手可能な実装を再現する。クラウド（claude.ai）セッションはCPU 2コアでGPUを持たないため、推論のみの再現とパイプラインのスモークテストを実行する。学習はすべて、`configs/`以下の設定ファイルと1行のコマンドを添えて、メンテナのマシンまたは研究室のGPUに引き渡す。

理由：文献の数値は、プロトコル（分割、評価指標、IoUしきい値）が異なると比較できない。少数のオープンなモデルを一つの固定プロトコルで自ら測定すれば、後のOpenTSRモデルと比較できるベースラインが得られる。

検討した代替案：いきなりモデル学習から始める（不採用：測定の基準となるベンチマークがまだない）。CPUで学習する（不採用：2コアで1280 pxの60エポック学習を行うと数日かかり、いずれにせよGPUでの学習結果とは一致しない）。

## 2026-10-31：評価指標はフレームワークではなくリポジトリ内に置く

決定：`src/opentsr/metrics.py`は、PASCAL VOC AP（デフォルトは全点補間、VOC07の11点補間も選択可）と簡単な分類指標を実装する。YOLOベースラインについては便宜上Ultralyticsの`val`の結果（COCO方式の101点補間）も報告するが、異なるフレームワークのモデルを同一の方法で採点するため、OpenTSRの数値はすべてリポジトリ内の評価器で再計算する。

理由：SCRDet++はIoU 0.5でのVOC方式APを報告しており、DTLDとBSTLDのベースラインはさらに別の慣例を用いている。評価器を一つにすれば、この曖昧さがなくなる。

## 2026-10-31：ライセンスの問題が解決するまでUltralyticsはベースライン専用とする

決定：Ultralytics YOLO11（AGPL-3.0、重みも含む）は、学習済み検出器を得る最速の手段であるため、S2TLDで手早くベースラインを確立するのに用いる。ただし、OpenTSRが公開するモデルのフレームワークとしてはまだ採用しない。次に評価するApache-2.0またはMITの代替候補：YOLOX（Apache-2.0、Autowareのfine detectorも使用している）、寛容なライセンスのRT-DETR / D-FINE / RF-DETR系の検出器、MMDetection（Apache-2.0）。

理由：OpenTSRは、コード、データ、重みをコピーレフトの義務なしに商用利用できるようにしたい。AGPL-3.0のツールで学習した重みはUltralyticsによってAGPL-3.0としても扱われ、重みをApache-2.0で公開することと衝突する。

## 2026-10-31：主対象を道路標識とし、信号機は副トラックとする

決定：OpenTSRの主対象を、信号機から道路標識（道路標識の検出と分類）に変更する。これまでの信号機に関する作業（データセットと実装の調査、S2TLDの分割マニフェスト、Autoware、COCO-YOLO、DetectionBenchの再現）は副トラックとして残し、削除しない。

理由：メンテナの判断による。信号機の結果は参照として引き続き有用であり、共有部分（評価器、分割マニフェスト、ライセンス方針）は標識にもそのまま引き継がれる。

検討した代替案：信号機の作業を削除する（不採用：測定には相応の労力がかかっており、結果は今も有効である）。信号機用に別リポジトリを作る（当面は不採用：両トラックは評価器と規約を共有しており、リポジトリを二つにすると保守の手間が倍になる）。

## 2026-10-31：リポジトリ構成で二つのトラックを分離する

決定：リポジトリのルート（`docs/`、`configs/`、`scripts/`、`src/opentsr/signs/`）は道路標識に属する。信号機に固有のものはすべて`traffic_lights`というパス要素の下に置き、それ以外の場所には置かない：

- ルートの`traffic_lights/`：信号機のREADME、文書、設定、スクリプト、Makefile
- `src/opentsr/traffic_lights/`：信号機のPythonパッケージ
- `data/traffic_lights/`、`weights/traffic_lights/`、`runs/traffic_lights/`：信号機のローカルファイル（gitignore対象）

両トラックで共有するコードは`src/opentsr/`の直下（`metrics.py`、`splits.py`）に置き、`opentsr.traffic_lights`からimportしてはならない。プロジェクト全体に関わる決定は本ファイルに記録し、信号機のみに関わる決定は`traffic_lights/docs/decisions.md`に記録する。

理由：一つの規則（「信号機の資料は常に`traffic_lights`の下に置く」）によって、標識の作業が増えてもトラックが混ざらず、後で副トラックを一度の`git mv`で削除または分離できる。

検討した代替案：ルートに`signs/`と`traffic_lights/`のフォルダを対称に置く（不採用：主トラックの階層が副トラックと同じ深さになる）。共有フォルダ内でタグやファイル名の接頭辞によって区別する（不採用：間違えやすく、grepしにくい）。

## 2026-10-31：GTSRB（公式分割）を最初の標識分類ベンチマークとし、検出の確認にはGTSDBを用いる

決定：GTSRBの公式分割（train 39,209 / test 12,630、43クラス）を、標識の最初の固定分類ベンチマークとする。データはHugging Faceのミラー`bazyl/GTSRB`（Kaggle版のparquetエクスポート）から読み込み、リビジョンとsha256を`scripts/prepare_gtsrb.py`で固定し、使用前に分割サイズとクラスIDを公式の数値と照合する。`tanganke/gtsrb`ミラーは、その26,640枚のtrain分割が公式の学習セットではなくIJCNN 2011 Phase Iのサブセットであるため、学習には使わない。これで学習した数値を比較に用いる場合は、その旨を明記する。GTSDBは検出の確認に用いる。テスト用300フレームの正解データはsid.erda.dkでホストされる公式のFullIJCNN2013アーカイブにしか存在せず、クラウドセッションからはそこにアクセスできないため、クラウドセッションでは公式のgt.txt付きの学習用600フレーム（852ボックス、ネガティブ94枚）を用いる。スクリプトは`--full-gt`を受け付けるため、メンテナはローカルで本来のテスト分割を採点できる。

理由：GTSRBは、利用条件（"The data is free to use"、論文を引用すること）が派生したクロップとラベルの再配布を認め、テストラベルが公開されており、文献に2011年から2026年までの比較可能な数値が数十件ある唯一の標識データセットである。GTSDBは、GTSRBとクラスIDおよびライセンス表記（"free to use this data package for any purpose"）を共有する。

検討した代替案：TT100KまたはMTSDを最初の検出ベンチマークにする（当面は不採用：どちらも非商用で、どちらも大規模である。これらはポインタ配布の評価セットとして残す。`docs/datasets.md`の第8節を参照）。torchvisionのGTSRBローダを使う（不採用：sid.erda.dkからダウンロードする）。

## 2026-10-31：標識のベンチマークのティアは信号機の方針に従う

決定：標識の分類・検出ベンチマークは、信号機と同じティアで整理する。Tier A（再配布可能、OpenTSRが固定分割を配布）：GTSRB、GTSDB、Synset Signset Germany（CC BY 4.0）、ZenodoのCC BY 4.0版から取得するCURE-TSRとSTS、ZOD（CC BY-SA 4.0、派生ラベルにも継承（SA）が及ぶ）、Panoramaxのクロップセット（CC BY-SA 4.0）。Tier B（非商用、テストラベル公開、ポインタ配布のみ）：TT100K、MTSD、DFG、BTSD、RTSD、CCTSDB。Tier C（要登録）：現時点では不要。日本についてはどのティアにも公開データセットがないため、日本のベンチマークは、Mapillaryの画像（CC BY-SA 4.0）または独自に撮影した映像に、パブリックドメインである標識令のピクトグラムの合成レンダリングを加えて構築する必要がある。詳細と規模は`docs/datasets.md`の第8節にある。

理由：信号機と同じ理由による。OpenTSRが再配布するものはすべて商用利用可能でなければならず、非商用のセットも数値の報告には使える。

## 2026-10-31：サードパーティのチェックポイントは制限付きunpicklerを通してのみ読み込む

決定：サードパーティによるUltralytics形式の`.pt`ファイル（完全なpickle）は、クラウドセッションでは`YOLO()`や`torch.load(weights_only=False)`で読み込まない。その手順は`scripts/eval_panoramax_de_classifier.py`に示してある。`pickletools`でpickleを逆アセンブルし、torch / torchvision / ultralyticsのモジュールのクラスからなる許可リストに含まれないものはすべて拒否し、まさにそれらのクラスだけを登録したうえで`torch.load(weights_only=True)`で読み込む。state dict形式のチェックポイント（例：poojahiraの`model_40.pth`）は、デフォルトの`weights_only=True`で読み込める。

理由：pickleは読み込み時に任意のコードを実行できる。素性の分からない数十のアカウントから重みを取得する調査で、それらを無条件に実行してはならない。制限付きローダは、正しい形式のチェックポイントに対しては何のコストもかからない。

## 2026-10-31：標識のCPUでの再現結果を比較の下限とし、GPUでの実行は場当たり的に行わず待ち行列に入れる

決定：`docs/replication.md`にあるCPUのみでの再現（GTSRBでスクラッチから学習したCNN、公開チェックポイントの公式テスト分割での評価、CLIPのゼロショット（SigLIPは待機中）、小規模VLMの多肢選択、GTSDBでのオープン語彙検出器、Panoramaxのドイツ標識分類器の自身の検証セットでの評価）を、最初のOpenTSRモデルが上回るべき基準点とする。GTSDB / ZOD / TT100Kでの検出器の学習とVLMのファインチューニングはGPUのタスクであり、2コアで実行するのではなく、設定と想定コストを添えて同ファイルに列挙する。

理由：再現した数値は、主張の再現（poojahiraは主張値99.81に対して99.71、CLIP ViT-B/32のゼロショットは論文値32.2との比較）か、どの論文にもない測定値（GTSDBでのオープン語彙AP、GTSRBでのVLMの多肢選択）のいずれかである。新しいモデルを学習する前に、その両方が必要である。

## 2026-10-31：依存関係とローカルファイルもトラックごとに分ける

決定：構成の規則（「信号機の資料は`traffic_lights`というパス要素の下にのみ置く」）は、依存関係の固定、パッケージのextras、ローカルファイルにも適用する。ルートの`requirements.txt`は標識トラックの依存関係を固定し、`traffic_lights/requirements.txt`は信号機トラックの依存関係を固定する。`pyproject.toml`は共通の基盤（`numpy`、`PyYAML`）のみを必須の依存関係とし、`[signs]`、`[lights]`、`[train]`のextrasを提供して、インストール時に両者が決して混ざらないようにする。ローカルファイルも同じく分ける。標識は`data/`、`weights/`、`runs/`を直接使い（`data/gtsrb_hf`、`weights/poojahira`、`runs/gtsrb`など）、信号機は`data/traffic_lights/`、`weights/traffic_lights/`、`runs/traffic_lights/`を使う。`docs/`以下の標識の文書では信号機の資料を扱わない。共有ファイルは`README.md`、`CLAUDE.md`、`Makefile`、`pyproject.toml`、`docs/README.md`、`docs/decisions.md`、`docs/third_party.md`のみである。

理由：信号機と標識のデータ、コード、文書を決して混ぜないよう、メンテナから求められた。Autowareのラッパー向けにonnxruntimeとOpenCVを固定していたルートの`requirements.txt`が、両トラックが意図せずファイルを共有していた最後の箇所であった。

## 2026-11-01：データセットカタログは固定シードで公式アノテーションから自動生成する

決定：図入りのデータセットカタログ（`docs/dataset_catalog.md`、`scripts/make_dataset_catalog.py`）は、手作業で組み立てた文書ではなく、自動生成される成果物とする。サンプルは再現で用いるのと同じローカルのデータファイルから固定シードで抽出し、すべてのサムネイルはファイルとボックスまでたどれるようにし、データセットを追加するたびに`make catalog`でカタログを再構築する。MTSDについては、手軽なparquetミラーではなく公式のアノテーションJSON（`NgTMDuc/cl_dataset`ミラーから取得）からサンプルを抽出する。parquetミラーの整数カテゴリが、そのミラー自身のラベルファイルと一致しないためである。データセットが存在しない日本については、MLITの道路標識一覧のピクトグラムをタイル状に切り出して用い、この一覧を日本トラックのクラス一覧とする。

理由：メンテナから、クラス定義と実際のサンプルを含む網羅的なカタログを求められた。手作りのPDFは最初の新しいデータセットが加わった時点で古くなり、検証もできない。自動生成したものであれば、再生成して差分をとれる。MTSDのミラーの問題は、クロップを実際に目で見たからこそ見つかったものであり、それこそがカタログの目的である。

検討した代替案：データセット論文の図を貼り付ける（再配布のライセンスがなく、再現性もない）。日本についてWikimedia CommonsのSVGを使う（自動クライアントにはレート制限がかかり、そもそもMLITの一覧が公式の出典である）。Roboflow上の日本のデータセットを使う（小さすぎ、再配布可能でもない）。

## 2026-11-01：フェーズ0の骨格、最初のL3セットとしてのSTS、粗粒度分類体系 v1

決定：

1. `system_design.md` の切り替え可能なパイプラインを、固定された9スロットとして実装する。設定はスロットごとの YAML マッピングで、`null` は「オフ」を意味する。未知のキーは拒否し、検出器は null にできない。モデル不要のステージを先に登録し、OpenTSR が自前の重みを持つ前に、外部の検出器や分類器をフレームごとのダンプから L3 で評価できるようにする。ランナーは1フレームにつき1行の JSON を書く。
2. Swedish Traffic Signs データセット（Zenodo 19666339、CC BY 4.0）を、イベント正解を持つ最初のシーケンスセットとする。そのイベントファイルは派生データ（アノテーションは CC BY 4.0）であり、`configs/sts/` にチェックインし、`scripts/make_sts_events.py` で再生成し、リンカのパラメータをファイルに記録する。データセットの SIDE_ROAD 状態を関連性ラベルとする。
3. 粗粒度分類体系 v1（`configs/taxonomy/coarse_v1.yaml`）は形状と色の13族を持つ。各データセットは族の一覧に対して検証される対応表を持つ。GTSDB の競技カテゴリはその細分である（テストで確認）。日本はまだ対応付けていない。道路標識令の区分は法的なものであって視覚的なものではないため、日本の対応付けはピクトグラム単位で行う。
4. イベント指標の規約（`docs/pipeline.md` 第3節）はベンチマークの一部であり、`benchmark.md` への日付付き追記によってのみ変更する。

理由：計画のフェーズ0は、最初のモデルが固定されたプロトコルで測られるように、モデルより先にハーネスを求めている。おもちゃのデータではなく実際のアノテーション（STS）に対して評価器を書いたことで、さもなければモデルの数値を見た後に決めていたであろう3つの規約（フレームごとの最良メッセージ、記憶中の標識の帰属固定、不明ラベル）が表に出た。模擬検出は、各スイッチが正しい列を動かすことの確認にすぎない。

検討した代替案：ZOD Sequences を先にする（登録とアノテーションのカバレッジが不明で、より大きい）。CURE-TSD を先にする（ライセンス確認待ち）。おもちゃのシーケンスだけでイベント評価器を書く（motion トラッカーを必要とした疎ラベルの対応付け問題が表に出なかったはずである）。
